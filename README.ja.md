# ATORCH T3PでDOOM

[English](README.md)

[ビルド済みアプリとオフライン梱包](docs/PREBUILT.ja.md)

ATORCH T3P本体でFreedoomのE1M1を動かす実験的なネイティブ移植。起動すると内蔵240×240 LCDにFreedoomのバナーを表示し、そのままE1M1に入る。本体のボタン、タッチ、傾き、マイクで遊べる。

## 本体で遊ぶ

USB-Cオス端子を上に向けて持ち、ゲーム画面が出たら約1秒静止して傾きの中立姿勢を取る。

| 入力 | 操作 |
|---|---|
| 左ボタン | 短押しで1発、長押しで連射。メニューでは決定 |
| 右ボタン | 扉やスイッチを使う。メニューでは戻る |
| 両ボタンを700 ms長押し | メニューを開く／閉じる |
| タッチしてドラッグ | 移動・旋回。メニューでは上下ドラッグで選択 |
| 傾ける | 左右で旋回、前後で移動。タッチ中はタッチを優先 |
| 手拍子 | マイクが周囲の音量に慣れた後、1回で1発 |

発射と被弾で振動の長さが異なる。実機では手拍子1回で1発、モーターの振動中に誤発射しないことを確認した。メニューの **UAC MONITOR** は気圧をhPa、起動時からの相対高度をmで表示する。+3 m以上の上昇が続くと `UPPER DECK FOUND` が出る。気圧と高度の表示ロジックは模擬データで確認済み。[操作と診断](docs/CONTROLS.ja.md)。

## V66のPC操作とライブキャプチャ

V65はプレビューを表示しながら移動・発射できたものの、PC画面だけで遊ぶには更新が遅かった。V66では実機でPC画面を見ながらプレイできた。既定は **高速 60×60** で、細部を見たいときは **精細 120×120** に切り替えられる。ブラウザーに受信fpsと直近1枚の取得時間を表示する。実機の結果は体感によるもので、数値の報告はまだない。

WindowsにPythonとHIDAPIのバインディングを用意する。V65またはV66の実機テスト版でDOOMを起動し、側面のPC接続専用HID端子をつなぐ。ほかのT3Pコントローラーは閉じる。

```powershell
py -3 -m pip install hidapi
py -3 scripts/t3p_pc_controller.py
```

[PCコントローラー](http://127.0.0.1:50595/)を開いてキーボードを有効にする。WASDまたは矢印で移動・旋回、Spaceで発射、Eで扉やスイッチ、EscとEnterでメニューを操作する。プレビューの停止と、最新フレームのBMP保存もできる。

V66はファームウェアのソースとPCコントローラーを先行公開する。ビルド済みアプリとオフライン梱包キットの公開には、このプロジェクトに割り当てられたUSB IDが必要。共用の `1209:0001` は非公開テスト専用。手元での試験用ビルドは、下記のローカルビルドの準備を行い、最後のコマンドに `--revision 66 --release-app --package-doom --private-usb-test` を指定する。割り当て済みのIDを使う場合は、ビルドとPCコントローラーの両方に `--usb-id VID:PID` を渡す。[テストPIDの利用条件](https://pid.codes/1209/0001/)。

## これまでの経緯

- まず純正USB HIDで設定や測定値の読取りを確認。左ボタンを押しながら通電すると純正HID更新画面に入る。純正3.0.3の再書込みと通常USBへの復帰は実機で確認済み。T3Pの全Flashバックアップと独立したROM復旧は未確立。
- カラーバー、RGB565と表示範囲の確認、独立した基板初期化の順に進め、E1M1の開始地点とHUDを本体で描画できた。
- 初期の計測は約7.8〜7.9秒／フレーム。V12でDEFLATE復号を高速化し、V13で繰り返し展開が主な負荷だと確認した。V14でフラットと描画列のキャッシュを追加。V16とV20では展開頻度の高いページを選んで無圧縮にし、展開後のゲームデータはバイト単位で維持した。
- V17のDBI DMA試験ではゲーム画面がノイズになった。V18でアクティブ行の設定を修正し、LCD時間はV16の約310〜320 msから134〜138 msへ短縮。V19では4列バッファを2枚にし、描画とDMAを重ねた。
- V20の開始地点付近の2サンプルは **約0.87〜0.93秒／フレーム**。うちDEFLATE展開は約0.59〜0.63秒。この段階では左から画面が書き換わる様子が見えた。

- V21では120×120の色インデックスで1フレームを保持し、送信時に240×240へ拡大。左からの更新は目立ちにくくなったが、発射時にはまだ見える。V22とV23では頻出5ページを追加で無圧縮化。V23のフレーム時間は**最初1,217 ms、少し経ってから966 ms、発射時1,031 ms**。最初の帯の送信処理から最後のDMA完了までは**162〜163 ms**だった。

- V24でDBI分周セレクターを3から2へ変更し、送信区間は **83〜84 ms** に短縮。発射時の書き換えも目立ちにくくなった。当初の公称8 MHzという見積もりと実測の比率が合わないため、実周波数は未確認として扱う。
- V25では7ページを追加で無圧縮化。初期・静止後・発射時の写真は **1,040 / 704 / 900 ms／フレーム**、展開時間は **642 / 436 / 560 ms**。V26の4バイト単位コピーでは、3枚の写真から明確な改善は確認できなかった。
- V27で7ビットのハフマン先頭符号テーブルを追加し、V26のコピー変更は無効にした。全1,369ページ、ランダム読取り5,000件、非圧縮ブロックへの遷移を含む420ストリームをPCで検査した。
- V28とV29で従来の展開処理と先頭符号テーブルを比較。10フレームのウォームアップ後、30フレームの平均は **753 → 698 ms／フレーム**、展開は **496 → 452 ms**、送信は約 **83 ms**。各1回の測定で、固定のゲームリプレイではない。計測中のボタン無効化と最後の画面停止は仕様。[結果](analysis/native-doom-v28-v29-benchmark.json)。
- **V30**ではV29の展開処理を採用し、左ボタンの発射と連続プレイに戻した。ファーム本体はV27とバイト単位で同じで、追加の高速化はない。比較計測で効果を確認できた展開処理を通常プレイへ戻す版。V30で発射と連続プレイをユーザーが確認。試験時間は未計測。[実機結果](analysis/native-doom-v30-physical-success.json)。

- **V31は実機でゲーム表示と発射を確認したが、体感の明確な改善はなかった。** ハフマン検索を7ビットから8ビットへ広げ、展開時のスタック使用量が512 B増える。V30のゲームデータ、キャッシュ、通常操作を維持。1回の検索で読める符号が増える一方、テーブル構築の負担も増えるため、写真3枚から平均の改善率は判断せず、当時の計測済み基準版はV30。[実機結果](analysis/native-doom-v31-physical-result.json)。全1,369ページ、ランダム読取り5,000件、各幅864ストリームを検査済み。展開処理の検査は `python scripts/check_tinf_prefix.py --compiler <host-clang>` で再実行できる。

- **V32は実機でゲーム表示と発射を確認。速度向上は未確認。** 無圧縮の3ページで容量を確保し、展開負荷の目立つDEFLATEの4ページと合わせてLZ4へ変更。ゲームパックは1,828 B縮小し、展開処理追加後もFlashに2,052 Bの余裕がある。静的RAM使用量、残りのページの内容と保存形式、通常操作は維持。体感では改善の可能性があるとの報告だったが、初期・静止後・発射時の写真は985/756/880 msで、V31の977/738/761 msを下回らなかった。タイミングを揃えていない各1フレームの値なので、この時点ではV30を基準版とした。[実機結果](analysis/native-doom-v32-physical-result.json)。[形式・選択ページ](docs/GAME_PACK_FORMAT.md)、[ビルド記録](analysis/native-doom-v32-build-reference.json)。

- **V35／V36の内訳計測が完了。** 両方30フレーム、最終tic40、照合値 `C269CBCE` で一致。追加計測下では混在方式がわずかに遅く、**676 → 693 ms／フレーム**、展開 **428 → 444 ms**、圧縮読取り **17 → 20 ms**。無圧縮Flashコピーは両方 **2 ms**、展開済みページのコピー **6 ms**、初回CRC **0 ms**、送信 **83 ms**。読取りを含む描画区間は570／587 ms。前回の小幅な混在方式の優位は再現せず、各1回・追加タイマーやコード配置の影響もあるため一般的な高速化とは判断しない。通常プレイの基準をV30とし、次の試験でページ別の累積展開時間を調べた。写真下部の総バイト数・回数は未転記。[結果](analysis/native-doom-v35-v36-benchmark.json)、[手順と表示行](docs/BENCHMARK_V35_V36.ja.md)。

- **V37／V38のページ別累積計測は実機完走。** 同じ30フレームで従来V37は平均668 ms（展開428 ms）、混在V38は686 ms（展開444 ms）。最終tic 40・照合値 `C269CBCE` が一致し、送信は両方83 ms。上位8ページでも合計約84／91 ms／フレームで、展開負荷は多数のページに分散している。今回も混在方式の速度優位は確認できず。各1回・計測と配置変更を含む条件での結果。[数値とページ順位](docs/BENCHMARK_V37_V38.ja.md)。

- **V39／V40の実機比較が完了。SRAM内側ループによる速度向上は確認できず。** 同じ画像列で30フレームを完走し、最終40 tic・照合値 `C269CBCE` が一致。V39（Flash）は平均666 ms／展開425 ms、V40（SRAM）は668 ms／展開430 ms、送信は両方83 ms。両版の解凍オブジェクトは同一で、今回移した446 Bの効果は見られなかった。各1回の小差を退行とは断定しない。当時の通常プレイの基準版はV30。[結果とページ順位](docs/BENCHMARK_V39_V40.ja.md)。

- **V41／V42が実機完走。展開本体が主要な負荷。** 最終40 tic・照合値 `C269CBCE` が両方で一致。V41では1フレーム当たり木の準備約95 ms、展開本体約382 ms。V42の詳細標本は計測負担が大きく、符号時間の単純換算が全展開区間を超えるため関数別占有率には使わない。次は詳細計測を外し、短いリテラルの連続処理を比較する。[数値と制約](docs/BENCHMARK_V41_V42.ja.md)。

- **V43／V44が実機完走。短いリテラルの連続処理に実測の改善。** 両方とも30測定フレーム・最終40 tic・照合値 `C269CBCE` が一致。平均フレーム時間は **666→626 ms（約6.01％短縮）**、展開は **430→387 ms（10.0％短縮）**、送信は両方 **83 ms**。V43はV39と同じ解凍オブジェクト。V44は追加Flash 96 B・静的RAM増加なしで、パック・キャッシュ・クロック・表示経路は共通。各版1回の開始地点の固定tic試験であり、配置の影響や再現性は分離できず通常プレイ全般のFPSとはしない。平均時間の逆数は約1.50→1.60フレーム／秒で、さらなる改善が必要。次の版はV44の連続処理を採用した。当時の通常プレイの基準版はV30。[実機結果](analysis/native-doom-v43-v44-benchmark.json)、[手順と検証](docs/BENCHMARK_V43_V44.ja.md)。

## V58のローカルビルド

Python 3、指定のJieLi Windows pi32ツールチェーン、純正T3P 3.0.3を用意する。版とハッシュは [SOURCE_LOCK.json](SOURCE_LOCK.json) を参照。パッケージ作成時に基板コードのバイト列を照合するので、`git clone -c core.autocrlf=false https://github.com/inuchanbt/apdo-doom-on-t3p.git` で改行コードを維持する。

指定リビジョンのDMC100-Doom全体を別途取得し、LinuxやWSLなど上流のビルド環境で `make gen` を実行する。その作業フォルダの `build/conv/upstream.json` と `dl/freedoom-0.13.0.zip` をT3P側の生成スクリプトが読む。純正イメージを `Atorch/T3P Firmware Version 3.0.3.bin` に置き、T3P側で以下を実行する。

```powershell
$Pi32 = 'C:/path/to/JL/pi32'
$Converter = 'C:/path/to/DMC100-Doom'
python scripts/prepare_lowres_game.py --converter-root $Converter
python vendor/jl-misctools/firmware/fwunpack_newfw.py --dirname "local/unpacked/T3P Firmware Version 3.0.3.bin" "Atorch/T3P Firmware Version 3.0.3.bin"
python scripts/build_engine.py --toolchain $Pi32
python scripts/build_native_board.py --toolchain $Pi32 --doom --package-doom --revision 58
```

更新用イメージは `artifacts/native-doom-v58/T3P_NATIVE_DOOM_E1M1_V58_3.0.3.bin`。SHA-256は[V58のビルド記録](analysis/native-doom-v58-build-reference.json)で照合できる。`DO-NOT-FLASH` の付いたファイルは中間生成物。実機試験では測定用端子を空け、PC接続専用HID端子を使う。測定器として使うときは、左ボタンを押したまま通電して純正HID更新画面を開き、DcTesterで純正3.0.3に戻す。[純正復旧の実機記録](docs/RECOVERY_DECISION.ja.md)、[ライセンスと出典](THIRD_PARTY_NOTICES.md)。
