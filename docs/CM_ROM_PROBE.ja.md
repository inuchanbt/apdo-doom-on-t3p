# 一回接続のROM識別試験

2026-11-01。T3Pの全Flash読戻しはまだ行っていない。

`recovery/cm_rom_probe`は補助RP2350-USB-CM専用。
初期状態ではGPIOを入力、プルなし、USBホスト未開始とし、自動送信しない。
ネイティブCDC接続を開いて`ARM_ATTACH_ONCE`を明示的に送ると、弱プルアップ下で
両線Highの空ポート基準を確認して600秒（v1は120秒）だけ待機する。
両線Lowが100µs続いた場合に一回だけ固定キーを送る。
接続検知が有効な起動時刻を捉えるかは実機依存で、すべてのT3Pで使えるとは未確認。

波形は実測済みのD+クロック／D−データ、0x16EF、16bit。
PIO自身で出力を解除し、完了・欠乏・解除状態を確認する。
波形用PIOプログラム・ステートマシン・DMAを解放して入力へ戻し、1.2ms待って
別コアでPIO USBホストを開始する。一度送信した起動中は再度キーを送れない。
待機期限切れ、DISARM、CDC切断時には未発火の待機を解除する。

弱いプルアップ下のLowをACKとは判定しない。ROM候補`4C4A:2942`と
純正アプリ`0483:5750`のUSB識別を区別して記録する。
TinyUSBのMSC/HID/CDC/VENDORホストクラスは無効。
独自の識別専用クラスは既知VID/PIDのインターフェース記述子を受理するだけで、
エンドポイントを開かず、クラス要求・SCSIコマンドを送らない。
標準のUSBリセット・SOF・デバイス/設定記述子取得・SET_CONFIGURATIONは行う。
RAMローダー転送、Flashの読取り・消去・書込みは実装していない。

`BENCH_FRAME_AND_HOST`はT3Pを外したスコープ単独試験専用。
両線Low基準を確認し、一回の波形からホスト開始までを試験する。
このコマンドも一回制限を消費する。繰り返す場合は補助CMを明示的に再起動する。

検証済み:

- 実際のC接続判定: 接続済み入力での待機拒否、100µs条件、チャタリング、期限、再送拒否。
- PC側の6テスト: 機器/端子/状態の拒否、短い送信の非再試行、待機解除、ベンチ結果の確認。
- RP2350用UF2の4テスト、生成ELFにMSC/HIDホストクラスのシンボルがないこと。
- 補助CMでARM→DISARM、送信0回・ホスト未開始を確認。
- T3PなしのBENCHで一回送信、出力許可0、故障なし、ホスト開始を確認。
- 同BENCH波形をMHO984で捕捉し、16bit・時間幅一致（第8回）。

ビルド: `scripts/build_cm_rom_probe.py`。
生成物: `artifacts/cm-rom-probe-v2/RP2350_CM_ONE_ATTACH_ROM_PROBE.uf2`。
旧v1生成物とそのソースは`artifacts/cm-rom-probe`へ保持。
制御: `scripts/cm_rom_probe.py`（既定は状態受信、`--arm`は一回接続待機）。
生記録は`local/cm-rom-*.json`。この文書のベンチ試験をT3PのROM接続成功とは扱わない。

初回のT3P接続待機は両線Highのまま120秒で期限切れになった。
`local/cm-rom-target-attempt1.json`に`arm_expired`、キー完了イベントなし。
終了後の`local/cm-rom-after-expired.json`で`armed=false`、`used=false`、
`host_requested=false`、`fault=false`、`frames=0`を確認した。
スコープはWAITのままだったためSTOPへ戻した。新しいT3P波形は取得していない。
物理接続したというユーザーの返答は、この記録時点では未受領。
次回はユーザーが挿せる準備を確認してから改めて待機を開始する。

ユーザーから通常画面が点いたとの返答後、CMを読み返してキー送信0回・未使用を再確認。
待機外の通常起動であり、キー受信成否の結果にはしない。
ユーザーがT3Pだけを抜いて準備OKと回答してから、待機を10分へ延長したv2へ切り替えた。
波形ヘッダー・PIO命令・一回制限・USB引渡し処理はv1と同じ。
期限と再送拒否を含むCテスト、PC側7テスト、UF2形式4テストを通過。
第2回の待機記録は`local/cm-rom-target-attempt2.json`。最終結果は同記録で確認する。

第2回は実際に接続条件が成立し、T3Pへのキー一回送信を完了した。
出力解除0・欠乏なし・故障なしを確認し、ホスト開始後に純正HID`0483:5750`として認識。
ROM識別`4C4A:2942`は得られなかった。Flashアクセスは行っていない。
集約は`analysis/cm-rom-target-attempt2.json`。

同回のスコープは、キー送信前の短い過渡変化でEDGEトリガーが成立したと考えられる。
8msの保存波形は両線ほぼ3.3V、最低でもCH1=1.626V・CH2=1.382Vで、
0V付近の平坦部や16クロックが含まれない。ACKの有無やキーの実機負荷波形は判断できない。
図は`artifacts/cm-wave-scope/target2-insertion-only.png`。

ユーザーがT3Pだけを外したことを確認後、ファームは同じv2のまま明示的に再起動。
第3回は、スコープをCH2正パルス・幅8〜11µs・閾値1.5Vへ設定し、全項目を読戻し照合した。
キーのHigh約9.667µsに合わせ、短い過渡変化や長いHigh待機での先行停止を避ける。
コマンドは公式MHO900 Programming Guideの337〜340ページに従う。
`scripts/mho984_scope.py prepare-key-pulse --trigger-channel 2 --timebase 0.0005`。
第3回の接続待機は`local/cm-rom-target-attempt3.json`、スコープはWAITを確認。

## 第3回の実機結果（2026-11-02）

接続条件が成立し、キー一回の送信・出力解除・識別専用ホスト開始が成功。
再び純正HID`0483:5750`として認識され、ROM識別は得られなかった。
これはT3Pへの実際のキー送信として2回目（初回待機は未発火）。

パルス幅トリガーではキー本体を含む8ms・125MSa/s・両1M点を取得できた。
`scripts/analyze_cm_rom_capture.py --attempt 3`で、既存の生波形から
唯一の16クロック列を検出し、D−の`0001011011101111` = `0x16EF`を確認。
High 9.664〜9.672µs、Low 9.624〜9.632µsで、8nsの標本間隔と整合する。
最初のクロック立上りから最後の立下りは299.04µs、ADCクリップなし。
波形解析は`analysis/cm-rom-target3-wave.json`、図は
`artifacts/cm-wave-scope/target3-key-and-after.png`。

最初のクロック立上りを0とすると、送信後310〜340µsの平坦部は
D−約0.832V、D+約0.881V。その後400〜450µsでは各約0.010V・0.070V。
送信を解放した後の弱いバイアス・内部プルダウン・容量を含む観測であり、
このLowだけをROMによる能動的なACKと区別できない。
したがって「キーが接続中の測定点へ届くことを実測済み」、
「ROM受信・ACK・ROM列挙は未確認」を分けて扱う。

次は抵抗で既知のバイアスを与え、ROM側が能動的にLowへ引くかを測る案を検討。
ユーザーへ4.7kΩ前後（2.2k/3.3k/10kも候補）とジャンパ線の所有状況を質問した。
抵抗値・実装方法が決まるまでは追加配線・新しいキー送信を行わない。

ユーザーが10kΩを2本以上所有と回答したため、並列5kΩをGPIO10とD+の間へ入れる
[バイアス測定の準備](CM_ACK_BIAS.ja.md)へ進む。補助CM用v3を別の生成先に作成し、
抵抗経路の事前検査と観測後の入力復帰を追加した。配線と物理検査は未実施。

追記: ユーザー実測5.098kΩの抵抗1本をGPIO10とD+の間へ配線。
v3の導入、T3Pなしでの抵抗経路・キー・バイアス解除・ホスト切替の実測を完了した。
詳細は[バイアス測定の実機確認](CM_ACK_BIAS.ja.md)。第4回接続試験を待機中。

第4回完了: 抵抗バイアス中のD+は約2.59VでLow応答候補なし。
キー値・16クロックは実測一致し、その後の識別は通常HID。
電源投入と送信時刻を分離する次の切り分けを検討中。
