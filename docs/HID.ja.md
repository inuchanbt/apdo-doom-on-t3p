# 純正状態でのHID要求・応答

2026-10-31。接続中の純正3.0.2で設定読取りと測定値読取りに成功した。
更新モードには入っていない。Flash書込み、設定変更、モーター操作は行っていない。

## レポート番号と通信ヘッダー

配布4版すべてのHIDディスクリプターは、レポート番号を指定しない64バイト入出力。
Windowsの65バイト長は先頭のダミー番号0を含む。
`0x55`はデータ本体のヘッダーであり、USB HIDのReport IDではない。
配布INIの`report_id=85`だけからReport ID=0x55と解釈してはいけない。
[HIDAPIの仕様](https://github.com/libusb/hidapi/blob/master/hidapi/hidapi.h)でも、
番号なしレポートの`hid_write()`には先頭0を付けることが説明されている。

```text
HIDAPIへ渡す65バイト: 00 | 64バイトの通信データ
通信データの先頭:        55 05 ...
```

## 実機で確認した2種類

| 用途 | 通信データの先頭9バイト | 応答の先頭4バイト |
| --- | --- | --- |
| 設定の読返し | 55 05 09 03 00 00 00 EE FF | AA 05 40 03 |
| 測定値の要求 | 55 05 22 05 0B 00 8C EE FF | AA 40 62 05 |

要求は後ろを0で埋めて64バイトにする。HIDAPIのダミー番号を含めると65バイト。
受信したHIDAPIのデータは、この環境ではダミー番号が除かれた64バイトだった。
設定応答は末尾EE FFを持つが、測定値応答には同じ終端条件を適用しない。

測定要求は純正コード内の一時的なUSB接続フラグとカウンターを更新する。
設定保存や出力電圧変更を行う分岐ではない。
設定読返しは要求バッファに応答を組み立て、送信して戻る処理。
読返される3個の設定値はバイト8、9、13。項目の意味はまだ決め打ちしない。

`scripts/t3p_queries.py`はこの2つの固定要求だけを持つ。
任意データ送信、更新開始、設定変更、電圧操作、モーター操作の機能はない。
既定ではUSBを開かず、送信予定バイトを表示する。
`--live`時もVID/PID、Usage、製品名で対象を限定し、該当機器が1台のときだけ開く。
応答時間・サンプル数・待機時間に上限があり、応答不一致後は再送を続けない。

```powershell
# オフラインで内容確認
& 'D:\KM003C\.venv\Scripts\python.exe' scripts\t3p_queries.py

# 固定の設定読取り1回
& 'D:\KM003C\.venv\Scripts\python.exe' scripts\t3p_queries.py --live --query settings

# 固定の測定値読取りを5回/秒で20回
& 'D:\KM003C\.venv\Scripts\python.exe' scripts\t3p_queries.py --live --query measurement --samples 20 --period-ms 200
```

## 実機の検査結果

- 設定要求に対して、想定どおりの64バイト応答を受信。
- 測定要求20回に対して20回応答、8種類の異なる測定データを受信。
- 高精度PC時計で測った応答時間は中央値1.348ms、最大2.480ms。
  1個の短い要求と応答にかかるホスト側の時間であり、最大通信帯域や画面転送速度ではない。
- 読取り前後の設定応答64バイトは一致した。
- 本体は引き続き`ATORCH T3P V3.0.2`として応答。HIDハンドルは検査後に閉じた。

ローカル記録は`local/settings-query.json`、`local/settings-query-after.json`、
`local/measurement-series.json`。要約とファイル指紋は`analysis/hid-live-summary.json`。
最初の受信待ちで0件だったことは、今回の要求に対する応答成功で補足された。
この機器では少なくとも、要求するとデータを返す経路が動作している。

メーカーPCソフトの`0x42CC00..0x42CE8D`もAA 40 62 05の分岐を持ち、
オフセット8〜48の11個のlittle-endian符号なし32bit値を1,000,000で割る。
除数はPCソフト`0x478060`のfloat値とも照合した。
読取りツールは未確定の項目名を付けず、オフセット付きの換算値として出力する。
加速度・気圧・タッチ・マイクの生データをこのパケットで取得できたとは扱わない。

## 純正コードとの照合

`scripts/hid_evidence.py`は配布アプリ4版のSHA-256を固定し、受信分岐、
設定応答のヘッダー・末尾、ディスクリプターを検査する。
修正版3.0.2は命令配置が異なるため、別の位置と命令列で照合している。

| 配布アプリ | 受信関数のアドレス |
| --- | --- |
| 3.0.2 | 0x0C0C5908 |
| 3.0.2 修正版 | 0x0C0C6218 |
| 3.0.2 Beta | 0x0C0C6BBC |
| 3.0.3 | 0x0C0CB48C |

アドレスは静的解析用。実機の関数をアドレス指定で呼び出したものではない。
検査結果は`analysis/hid-protocol.json`。

## 通常通信と更新・復旧の区別

`55 05 09 02`は今回使った`55 05 09 03`とは別の更新開始処理。
NVRAMの`0x100214`へ`ubootZst`を書き、MMU停止・リセットへ進む。
T3Pの独自HID更新ブートローダーに入る経路であり、ROMのUSB強制復旧が確保された
ことにはならない。今回このコマンドは送っていない。
[更新ブートローダーと復旧経路](RECOVERY.ja.md)参照。
