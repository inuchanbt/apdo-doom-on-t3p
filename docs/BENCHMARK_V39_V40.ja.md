# V39 / V40：長いハフマン符号とSRAM実行の比較

2026-11-05作成・実機比較完了。**両版が同じ画像列で完走し、SRAM内側ループによる速度優位は確認できなかった。**
V37の従来パックを使い、10フレーム準備＋30フレーム測定する。

## 変更

- V39：7ビットの検索表に収まらない符号を、8ビット目から続けて読む。
  従来は検索に失敗すると1ビット目から木をたどり直していた。
  検索表の未使用エントリーに途中の位置を保存し、符号の木・検索表・
  展開用スタックのサイズは増やさない。`counts[0]` は構築後のみ途中の基点に再利用する。
- V39とV40は同じ属性・コンパイル条件で、内側の2関数を専用セクションへ分離。
  **`tinflate.c.o` はバイト単位で同一**。V39はFlash、V40は通常のSRAMで実行する。
  セクション分離によるコンパイラーの判断変更もあるため、V37→V39の差を
  符号処理の変更だけに帰属させない。
- V40：`tinf_decode_symbol`（222 B）と `tinf_inflate_block_data`（224 B）を
  SRAMの `0x101A80` と `0x101B60` へ配置。起動時に既存の初期値コピーで転送し、
  コピー後の `csync` をリンク済み命令でも確認。木の構築・一部ヘルパー・定数表はFlash。
  CPU、SFC、I/Dキャッシュの設定レジスターは変更していない。
- これは命令読出し経路を変える比較。キャッシュ無効やスラッシングが起きていると
  確認したものではない。速度差がなくてもSRAM実行が失敗したとは判断できない。
- ゲームパックはV37/V39/V40で完全一致。ページキャッシュ35枚、
  120×120の色インデックス画面、LCD送信、ゲーム時計、ページ順位の計測条件も共通。

## 試験手順

1. V39を書き込んで通常起動し、ボタンを押さずに待つ。
2. 3行目が `0000D00E` になったら、左上の**全30行**を撮影する。
3. V40でも同じ手順を行う。

| 表示 | V39 | V40 |
|---|---|---|
| 1行目（版、16進） | `00000027` | `00000028` |
| 2行目（測定30フレーム） | `0000001E` | `0000001E` |
| 3行目（完了） | `0000D00E` | `0000D00E` |
| 13行目（最終40 tic） | `00000028`確認済み | `00000028`確認済み |
| 14行目（画像列照合値） | `C269CBCE`確認済み | `C269CBCE`確認済み |

4〜6行がフレーム全体、7〜9行が展開、10〜12行がLCD送信の
平均・最短・最長（16進ms）。15〜30行はV37と同じページ別上位8件。
入力無効と最後の停止は計測版の仕様。通常プレイの基準版はV30。
実機で照合値・完走を確認するまでは、高速化成功とも安定版とも扱わない。

## 検査と再現

- 7/8ビットの従来・継続方式、および実機向け属性を付けた7ビット方式の5構成。
  各2,215ストリームでPython zlibと一致。実パックの圧縮1,343ページ、
  最大15ビットの符号と8通りのビット位置、重複コピー、圧縮ブロックから非圧縮ブロックへの境界を含む。
- 読取り経路の全1,369ページ・ランダム範囲5,000件・破損と範囲外の拒否、
  累積時間のリセット・キャッシュ命中・再展開・飽和・上位8件を確認。
- 66件の回帰テストを通過。ゲーム進行処理の変更はない。
- ELFでコードの実行先とFlashロード元、初期化対象、RAM/Flash境界を確認。
  V39をSRAM配置と誤認すると検査が失敗することも確認。
- 独立したファーム展開ツールで両版を読み直し、app.binが作成したペイロードと一致。
  純正3.0.3のその他46エントリーと先頭20 KiB・リソース末尾を保持。

```
python scripts/check_tinf_prefix.py --packed artifacts/native-doom-v37/E1M1-2k.t3pg
python scripts/check_game_pack.py --page-totals --prefix-continuation --packed artifacts/native-doom-v39/E1M1-2k.t3pg
python -m unittest discover -s tests -p "test_*.py"
python scripts/build_native_board.py --toolchain <JieLi-pi32-directory> --doom --package-doom --revision 39
python scripts/build_native_board.py --toolchain <JieLi-pi32-directory> --doom --package-doom --revision 40
```

Windows x64での初期実験では、途中から読む変更だけの全圧縮ページ展開は
9サンプルの中央値で約3.5％短縮した。これは専用セクションを付ける前のPC上の参考値で、
完成したV39/V40の実機速度やフレームレートの予測には使わない。
ビルド記録は `analysis/native-doom-v39-build-reference.json` と
`analysis/native-doom-v40-build-reference.json`。

## 実機結果：2026-11-05

ユーザーが両版を書き込み、最終画面を撮影。先頭 `27` / `28`、
30フレーム完了 `D00E`、最終40 tic、画像列照合値 `C269CBCE` が両方で一致。
各版1回、入力なし開始地点の比較であり、移動・発射や長時間安定性の試験ではない。

| 区間（ms） | V39 Flash：平均／最短／最長 | V40 SRAM内側ループ：平均／最短／最長 |
|---|---:|---:|
| フレーム全体 | 666／639／720 | 668／641／735 |
| 圧縮ページ展開 | 425／402／480 | 430／402／458 |
| LCD送信区間 | 83／83／84 | 83／83／84 |

平均からの換算は約1.50 fps。V40はフレームが2 ms（0.3％）、展開が5 ms長かった。
この小差と各1回の測定から退行とは断定しないが、**今回移した446 Bによる高速化は確認できない**。
前回V37の668 ms／展開428 msと比べても大きな変化はない。
V37→V39はコードのまとめ方と配置も変わるため、符号継続処理だけの効果にはしない。
通常プレイの基準版はV30を維持する。

|---|---|---|
| 1 | `544`／323／60 | `535`／327／60 |
| 2 | `535`／321／60 | `544`／318／60 |

ページ番号は16進、時間・回数は10進。すべてDEFLATEで、パックの方式フラグとも一致。
上位8枚の合計は80.4／80.7 ms／フレーム。全展開425／430 msの一部にとどまり、
特定の数枚だけへの対策で全体が劇的に改善するとは期待できない。

今回の結果は、Flashに残る木の構築・ビット読取りヘルパーや、描画側の命令読出しまで
否定するものではない。また、I/Dキャッシュが無効・スラッシング中という証拠にもならない。
解凍内部の時間配分はまだ測定していないため、残った関数のどれが支配的かは未確定。

`analysis/native-doom-v39-v40-benchmark.json` に保存した。写真自体は配布しない。
