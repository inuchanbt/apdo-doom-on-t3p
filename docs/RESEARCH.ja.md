# T3P 調査記録 — 2026-10-31

## 実機で確認したこと

- USB: VID `0483` / PID `5750`、製品文字列 `ATORCH T3P V3.0.2`、メーカー文字列 `APP`。
- HID: Usage Page `FF02`、Usage `0002`。
- Windows上の入力／出力レポート長はどちらも65バイト。
  配布4版のディスクリプターは番号なし64バイト入出力。送信はダミー番号0＋通信データ64バイト。
  通信ヘッダー0x55はHIDのReport IDではない。
- Featureレポート長は0。
- 初期の受信待ち5秒は0件だった。その後、固定の設定・測定値要求で応答を取得できた。
  測定値20回の要求に20回応答。読取り前後の設定応答も一致。[通信の詳細](HID.ja.md)参照。
- 初回の共有違反は別製品用の `KWS-X1 OTA 英文版` が原因。
  T3PのHID PDO `\Device\000001e6` を保持するハンドルをPID 34020で確認し、
  所有者がそのツールを終了した後にHIDを開けるようになった。

識別・受信結果: `local/hid-working.json`。
個体シリアルとWindowsのデバイスパスを含むため、公開用には扱わない。

## 配布ファームの解析で確認したこと

提供場所: `Atorch`。元ファイルのSHA-256とサイズは
`analysis/stock-inventory.json`、展開結果の検証は `analysis/stock-verification.json`。

全4種で以下が一致した。

- JieLi新形式フラッシュヘッダー、PID文字列 `AC707N`。
- `app_dir_head` のファイルオフセット `0x5000`、`app.bin` は `0x5100` から。
- アプリのエントリーアドレス `0x0C000100`。
- 設定内から得たアプリ領域の暗号化キー `0x8D07`。
- 展開済み `uboot.boot` は4種とも同一SHA-256。
- アプリのヘッダーCRC・データCRC、および再暗号化したアプリと元ファイルの該当範囲が一致。

| 配布ファイル | アプリのバイト数 | アプリCRC16 |
| --- | ---: | --- |
| T3P-APP-3-0-2.bin | 1,413,216 | D5B9 |
| T3P-APP-3-0-2(修复版本).bin | 1,418,592 | C2EA |
| T3P-APP-3-0-2(最新Beta版本).bin | 1,444,000 | A857 |

ヘッダーのFlash sizeは `0x1FF000`、`key_mac` は `0x1FF000` の4KiB領域を指す。
これは2MiBの構成を示唆するが、実チップ容量を読み出した結果ではない。
配布ファイルには全領域が含まれず、校正や個体情報まで確保した実機バックアップではない。

## ネイティブ解析で増えた根拠

対象は**配布3.0.3**。接続中の3.0.2で同じ関数アドレスを使えるとは扱わない。
`scripts/hardware_evidence.py` が展開アプリのSHA-256、26か所の命令、液晶／I2C設定、
加速度初期化テーブルを検査し、`analysis/hardware-3.0.3.json` に記録する。

| 部分 | 純正3.0.3から読み取れた内容 | 実機で残る確認 |
| --- | --- | --- |
| 液晶 | 登録ドライバーは1個、`st7789v`。RGB565、SPI4線設定。リセットPC00 | 実パネルと描画・向き |
| 液晶サイズ | パラメーターの入力／出力は320×320、バッファ12,800バイト×2、設定60fps | 初期化2A/2Bの終端は239。物理解像度はまだ確定しない |
| バックライト | `IO_LCD_PG`=0xE7を使う特殊出力 | 明るさ制御。GPIO E7ではない |
| I2C | 設定と初期化ルーティングはSCL=PA06、SDA=PA05、100kHz | 実配線とバス動作 |
| タッチ | CST816D系。7bitアドレス0x15、リセットPA02、割込みPB08。0x02から5バイト読取り | 実座標の向き・端・押下解除 |
| 加速度 | 7bit 0x19、0x0FでID 0x11を検査。SC7A20公式SDKと初期化8組が全一致 | 実ID、軸方向、感度、更新速度 |
| 加速度データ | FIFO状態0x2F、0xA8から6バイト、各軸の符号付き16bit値を4bit右シフト | ゲーム用の中立位置・傾き換算 |
| 気圧 | 7bit 0x77、0xD0でID 0x58、0x88から24バイト校正、0xF7〜FCの生値。BMP280の配置と一致 | 実IDと個体校正値、圧力補償と反応速度 |
| モーター | `IO_MT_PG`=0xE8で特殊PWM出力を初期化する処理 | 実振動、強さと時間 |
| マイク | 経路／チャンネルの特定は未了 | 音量値や波形の取得 |

SC7A20／BMP280は、純正コードが想定する互換系列の判定。チップ刻印や実機読取りによる
製造元確定ではない。気圧読取り試作の出力は生ADC値であり、Paや温度ではない。

液晶登録はRAM `0x11F678`、パラメーターは`0x120164`。
UI起動側`0x0C0708AE`が設定`0x0C111A08`をUIタスクに渡し、
タスクが登録インターフェース`0x0C0B6A48`の初期化を呼ぶ経路まで追跡した。
I2C設定は`0x0C111A10`。加速度初期化表は`0x0C15A1EC`。

公式SDKの固定DBI端子定義はCS=PA07、DC=PA13、CLK=PA12、D0=PA08。
これはSoCの定義であり、基板実測とは区別する。SDKのCST816D初期化にはタッチICの
自動更新処理も含まれるので、調査用読取りヘルパーにはその初期化を取り込んでいない。

### メモリとビルド

純正起動コードはBSS `0x101A80..0x11F0E0` を消去し、
Flash `0x0C161B80`からRAM `0x11F0E0`へ0x1B80バイト、
続いてFlash `0x0C163700`からRAM `0x120C60`へ0x2740バイトをコピーする。
主ヒープ初期化の範囲は`0x1233A0..0x136E00`、80,480バイト。
これは純正の初期化時範囲であり、実行中の空き容量ではない。

独立リンク検査では`0x101A80..0x136E00`の217,984バイトを仮のRAM領域に使用。
入力・センサー・圧縮読取り・液晶出力変換を含む87オブジェクトをpi32v2/r3でビルドし、リンクが成功した。

| 検査ELFの領域 | バイト数 |
| --- | ---: |
| コード＋読取り専用定数 | 128,482 |
| 圧縮ゲームデータ | 1,189,607 |
| 初期値付きデータ | 82 |
| BSS | 89,328 |
| 静的RAM合計 | 89,410 |
| RAM配置の整列を含む占有範囲 | 89,424 |
| Flash配置の整列を含む占有範囲 | 1,318,173 |

4KiB×8の展開キャッシュと液晶用作業領域を静的RAMに含む。仮のRAM領域内の残り128,560バイトは
スタック、実機ドライバー、通信・描画バッファを差し引く前の値。
仮のFlash領域0x1F0000バイトには残り713,443バイトあるが、実起動コード・
ドライバー・実機向け配置が未確定なので実機での収まりを断定しない。
動作可能性や実フレームレートの証明にはしない。
汎用PSRAM文字列や追加アドレスの存在だけで利用可能RAMを水増ししない。

Windows用にも同じエンジン・ブリッジ・入力・圧縮読取りをコンパイル。
圧縮データでE1M1を起動し、140描画フレーム＋35操作ステップを通した。
仮の傾きで前進・旋回、ボタンで射撃、2ボタン長押しでメニューへ移ることを確認。
2ページから8ページにキャッシュを増やしても、保存した全6フレームとプレイヤー状態が一致。
同じPC上で175ステップの所要時間は16.791秒から8.001秒に減った。
これはPC上の経過時間であり、MCUのフレームレートへ換算しない。
キャッシュミスは124,661から59,125回に減ったが、実機ではさらなる調整が必要な可能性がある。
記録は`analysis/simulator-cache-2.json`、`analysis/simulator-cache-8.json`。

## 純正PCソフト

`01-T3P_PC_Application_V1.0.9/DcTester.exe` は32ビットのQt5アプリ。
HIDAPIのlibusb側の処理を含み、VID/PID `0483:5750` の定数がある。
同梱INIの `report_id=85` は `0x55` と一致する。
このINI名をUSBのReport IDと解釈しない。実際のディスクリプターにはReport ID指定がなく、
今回の送信ではダミー番号0の後ろに通信ヘッダー0x55を置いて応答を得た。

Qtのメソッド名と静的ディスパッチの対応を抽出した。
`analysis/map_pc_slots.py` はこの配布EXEの配置専用であり、別版には流用しない。

| メソッド | PCアドレス |
| --- | --- |
| usbreceivedata | 0x004067A0 |
| usbconnect | 0x00424760 |
| mytimer_timeout | 0x00406450 |
| on_disp_Btn_Run_clicked | 0x004249E0 |
| on_upgrade_pushButton_start_clicked | 0x004117A0 |
| on_settings_btn_M_open_t3_clicked | 0x0040B880 |
| on_settings_btn_M_close_t3_clicked | 0x0040BA30 |

更新開始処理が `0x00410870` を経由して `55 05 09 02 00 00 00 EE FF` を構築する。
これは通常の情報読取り要求として扱わない。本体には送信していない。
更新処理には反転型 `0xA001`、初期値 `0xFFFF` のCRCループもあるが、
パケット全体の仕様や実機動作はまだ確定していない。
メーカーPCソフトの実行・ボタンクリックによる機能テストも未実施。

## DOOMへ向けた次の段階

1. 純正状態のHID要求応答は確立。通常データにないセンサー値の取得方法を調べる。
2. 液晶のサイズ・描画と、T3Pのタッチ／センサー／モーターを実機で確認する。
3. スタック・ドライバーを含む実メモリ使用量、Flash、描画バッファの収まりを確かめる。
   ゲームデータをPCから供給するKWS-X1方式も候補。ただし通信速度は未計測。
4. 実機全体の読戻しと復旧経路を調べ、個体のバックアップを確保する。
5. 最小の画面描画・タッチ読取りから始め、DOOM・タッチ操作・被弾時振動へ進む。

ネイティブDOOMのコンパイルと仮入出力によるオフラインリンクは成功したが、
実機の起動用ファームは未完成、実機では未実行。
既存のKM003C／KWS-X1のARMバイナリはそのまま使えない。
