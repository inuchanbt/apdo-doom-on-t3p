# 純正HIDブートローダーを残す経路の机上検証

2026-11-02。USB/シリアルへ一切接続せず、メーカー配布4版を解析した。
結論は「通常配置でブート領域を残す構造を確認」。実機への書き込み許可や、
個体全体を復元できる保証ではない。手動のCM/スコープ試験は停止を維持する。

## アプリより前にあるボタン分岐

4版の`uboot.boot`は同一SHA-256：
`53b7b7f6ec1711becb538625a5afe4b45cc3dba5fafee8bcb229bd12d0791ec1`。
配布ファイルのこのコード自体に更新モードへの分岐がある。

- `0x103ea0`でPORTA基準`0xfd3000`を作り、PA11を入力・プルアップに設定する。
- `0x103eca`でRAMタグ`ubootZst`を比較する。
- タグ一致、検査フラグr9が非ゼロ、またはPA11 Lowで`0x103edc/0x103ee0`の更新経路へ入る。
- それ以外は`0x1041ca`以降の通常アプリ検査・実行へ進む。アプリの間接呼出しは`0x104c8e`。

したがって、更新モードのボタン分岐は通常アプリの実行に依存していない。
ユーザーの実機では左ボタンを押したまま通電し、HID更新画面へ入ることを確認した。
PA11とボタンの電気的な導通自体は測定していない。
アプリの任意の破損が自動的に検出される、とまでは判断しない。

## 通常配置の更新先

`0x1041b4..0x1041c4`で`app_dir_head`を開き、ファイル文脈の先頭を更新先にする。
配布4版のルートエントリーは共通で`app_dir_head=0x5000`。
ブート本体の配布範囲は`0xc0..0x46b0`、その後の設定も`0x5000`より前に収まる。

有効AAヘッダーでファイル文脈を再オープンし、`0x1046da`から消去へ進む。
文脈の先頭＋カーソルをアドレスにし、配布ヘッダーのalign16×256=4096バイト単位で消す。
純正のファイル長はいずれも4KiB境界なので、この条件では消去範囲は
`[0x5000, 配布ファイル長)`となる。先頭20KiBと`key_mac=0x1ff000`には届かない。

**重要な例外：** ROMから渡された実行時Flash基準が`0x10000`のとき、
`0x104136`以降はUSB初期化より前に消去・コピーによる配置移行処理へ分岐する。
そのため「ボタン起動は常にFlash無書込み」とは言えない。
今回の配布ファイルはbase0だが、接続中の個体の実Flash配置は未読出し。
ここを飛ばして、実機のボタン起動を読み取り専用の検証とは扱わない。

## 個体設定は別に考える

VMの予約位置は版によって変わる。大きい版の更新範囲は、小さい旧版のVM候補位置を
越える。4版の組合せには6ケースある。VM位置を絶対/アプリ相対のどちらと読むかも
実機では未確定なので、両方の候補を報告書に残した。

ブート領域が残ることと、校正・個体設定まで残ることは同じではない。
カスタムアプリで領域を不用意に拡張せず、配布済みの最小アプリ枠とファイル長を維持する
設計が有力。ただし、個体の版と設定保存先の照合はまだ必要。

## ファイル構成と容量の検証

`check_stock_app_container.py`は4版すべてに対して、次をメモリ内だけで検証した。

1. 純正アプリをそのまま戻すと、暗号化後のファイル全体が元ファイルと完全一致。
2. 1バイトだけ変える検査では、アプリCRC、内側エントリーCRC、外側領域CRCを更新できる。
3. 先頭20KiB、VM/PRCT/BTIF/EXIFのエントリー、アプリ外リソース・末尾は不変。
4. 枠を1バイトでも越える入力は拒否。

検査用の変更データは破棄し、更新用binは生成していない。
最小純正app.binは1,413,216バイト、既存DOOMリンク試作のFlash使用幅は1,318,173バイト。
差は95,043バイト。実起動処理・実ドライバーを入れる前の容量差であり、完成見積もりではない。
`DO-NOT-FLASH-linkcheck.elf`は引き続き書込禁止。検査スクリプトのペイロードには使っていない。

## 再現と次の確認

```powershell
& 'D:/KM003C/.venv/Scripts/python.exe' scripts/audit_stock_recovery.py
& 'D:/KM003C/.venv/Scripts/python.exe' scripts/check_stock_app_container.py
```

根拠：`analysis/stock-recovery-audit.json`に48か所の実バイトと9呼出し先、
4版の条件付き更新範囲を記録。コンテナー検証は`analysis/stock-app-container-check.json`。

純正PCソフトもSHA固定で静的解析した。Qtのメタデータと実際のx86呼出しから、
更新開始・ファイル読込・受信処理など5関数を特定した。静的解析時点ではソフトを実行していない。
更新開始関数はAA06とファイルサイズ/58からのパケット数を送る。
PCではbyte4がCRC下位、受信側では同じbyte4を末尾長計算に読む食い違いがあるため、
推測で新しい送信器は作らない。ただし純正の4KiB整列サイズでは、受信コードの
実際の整数演算でbyte4全256通りを計算しても、上記の消去終端は変わらなかった。
4版×256条件を照合済み。`analysis/stock-pc-updater-audit.json`を参照。
調べた更新処理では、現在のFlash配置を安全に取得できる要求は確立していない。
この結果は、PCソフト全体に読み出し要求が絶対存在しないという証明ではない。

ユーザーが左ボタンを押したまま通電し、「Product upgrading / Channel:HID / Model:T3P」
画面を提示した。列挙だけの確認でも0483:5750、usage FF00:0001、メーカーIAP、
製品ATORCH T3P V1.0.1を確認。通常アプリのFF02:0002とは異なり、配布ブートの記述子と一致。
根拠は`local/t3p-stock-boot-identity1.json`と`local/recovery-evidence/t3p-HID-upgrade-user-photo.jpg`。

購入時の版は不明。現在は3.0.2 Betaだった可能性が高いというユーザー申告であり、
正確なビルドは未同定。ユーザーは純正正式版3.0.3への復旧を許容している。

純正DcTester V1.0.9を実行し、接続機器T3P IAP V1.0.1を画面でも確認。
`artifacts/stock-restore-3.0.3/T3P Firmware Version 3.0.3.bin`を選択し、
読み込み完了、1,540,096バイト、進捗0を確認した。元ファイルとのSHA256一致も再確認。
この準備段階では「开始下载」を押さず、ユーザーの書込み承認を待った。
CMとスコープによるROMキー試験は再開しない。

## 純正3.0.3の実書込み結果（2026-11-02）

個体設定・校正の保持が未確認であることを伝え、ユーザーが「実行して良いよ」と承認。
メーカーソフトの「开始下载」を一度押して更新を実施した。
ログは握手成功、転送完了、書込み完了、今回の更新終了を表示。進捗100%、
ソフトが報告する所要時間130秒、転送速度11.57KB/秒。

自動切断・再接続後、メーカーソフトの表示がIAP V1.0.1からAPP V3.0.3に変わった。
独立したHID列挙でも0483:5750、FF02:0002、メーカーAPP、
製品ATORCH T3P V3.0.3を確認。通常測定画面でも受信値とグラフを表示できた。
UIのアクセシビリティ要素参照が失効したため、ホームへの移動は新しい画像に基づく座標で行った。
更新開始ボタンを再度押す操作は行っていない。

記録：`analysis/stock-restore-live.json`、`local/t3p-stock-3.0.3-post-restore.json`。
純正更新の入口から正式版へ戻る実機経路を確認できた。任意のカスタムイメージの
起動・復旧、全Flashバックアップ、校正値の保持、実機画面の表示状態は未検証。
