# RP2350-USB-CMを使う準備

2026-11-01更新。ユーザーの所有品は次の3種類。

| ボード | 今回の役割 |
| --- | --- |
| Waveshare RP2350-USB-CM（オス・メス） | 第一候補。通常USBとPIO-USBを分けて使う |
| RP2350B-Plus-W | 予備。必要に応じて波形確認等の別用途を検討 |
| M5Stack CoreS3 | 今回は予備 |

画像2はメス・メス版だが、ユーザーが持つのはオス・メス版。
[メーカー資料](https://docs.waveshare.com/RP2350-USB-C)ではオス側PIO端子を持つ機種は
RP2350-USB-CM、SKU34953として区別される。
CM用とC用のGPIO並びは異なるため、C用の設定をそのまま使用しない。

## 照合した資料と配線

メーカーリポジトリーの固定リビジョン:
`774cbb1e8ecc9d5cc8474ba9feb90a0939047f3b`。

- [CM回路図](https://github.com/waveshareteam/RP2350-USB-C/blob/774cbb1e8ecc9d5cc8474ba9feb90a0939047f3b/hardware/schematics/RP2350-USB-CM.pdf)
- [PIO設定ヘッダー](https://github.com/waveshareteam/RP2350-USB-C/blob/774cbb1e8ecc9d5cc8474ba9feb90a0939047f3b/examples/C/01_USB/src/pio_usb_configuration.h)
- [USBホスト＋CDCの例](https://github.com/waveshareteam/RP2350-USB-C/blob/774cbb1e8ecc9d5cc8474ba9feb90a0939047f3b/examples/C/01_USB/examples/host_hid_to_device_cdc/host_hid_to_device_cdc.c)

回路図のUSB-CメスType_C1はRP2350のUSB_DP/USB_DMへつながる通常USB。
オスType_C2はGPIO13→27Ω→D+、GPIO12→27Ω→D−のPIO用端子。
メーカーのCM用設定も`pin_dp=13`、`PIO_USB_PINOUT_DMDP`で一致する。
メス・メスのC版の設定はDP=12、DM=13。

両端子のVBUSはVSYSに接続され、回路図上に個別の電源スイッチはない。
オス側にはD+を3V3へ引くR10=1.5kΩ、D−側のR13=NC/1.5kΩ、
CCにR21=5.1kΩ、R19=NC/56kΩという設定もある。
USBホストやUSB_KEYの応答判定へ進む前に、実際の実装・電圧・抵抗の影響を確認する。
末尾にR10の同定・取り外し後の検査を記録。ホスト接続はまだ試験していない。

2ポートはデータ線が直結したUSBハブ・切替器ではない。
PCの通常USB CDCと、PIO側のUSBホストとの間をソフトウェアで中継する構成が候補。
メーカーにはキーボード／マウスを読む例があるが、JieLi用USB_KEY、
ROMへの引渡し、独自SCSI、全Flash読出しまで完成した例ではない。

## 最初の確認用プログラム（v1）

ソースは`recovery/cm_input_check`。
通常USBでPCのシリアルポートとして現れ、GPIO13/12の入力状態を1秒ごとに表示する。
PIO側GPIOは入力、内蔵プルアップ／プルダウンとも無効。
USB_KEY、USBホスト、T3P向けコマンド、電源切替は含まない。
外部抵抗による電圧は残るため、「入力」だから線が電気的に浮くとは限らない。

カスタムボード定義でFlashを2MiBとし、Pico 2のLED・SMPS・VBUS検出ピンを流用しない。
UART出力、1200baudによる自動リセットも無効にした。
シリアルで使えるコマンドは`STATUS`、`HELP`、このCM自身を戻す`BOOTSEL`のみ。

初回はCMのオス端子を空けて、メス端子だけをPCにつなぐ。
BOOTを押しながら接続してBOOTSELモードへ入り、ボードに今入っているプログラムを
読戻し・保存してから、確認用プログラムへ進む。
確認用ファイルは**補助RP2350ボード用**であり、T3Pの更新ファイルではない。

後でT3Pへ接続するときの対象は、現在PCにつないでいるHID専用端子。
測定用のType-C入出力へCMのオス端子を直接挿す手順にはしない。
初回の入力確認ではT3PをCMへ接続しない。

ビルドは`scripts/build_cm_input_check.py`。
固定したPico SDK 2.2.0とTinyUSBを使用し、ローカルでUF2とELFを生成するだけ。
取り外し可能ドライブへのコピーや書込み機能は含まない。
PC側の`scripts/capture_cm_input.py`もシリアルへデータを送信せず、
確認用プログラムのJSON出力を受信・検査する。

## 最初の実機確認（2026-10-31）

ユーザーの接続後はドライブではなくCOM9が現れた。
既存プログラム`usb_device`が通常モードで動作しており、公式picotoolで
この一台をBOOTSELへ切り替えた。ドライブ文字を使わずUSBから読み書きできた。

- 補助CMの全Flash 2,097,152バイトを`local/backups/cm-usb-device-original.bin`へ保存。
  `picotool save -a -v`による実機との照合はOK。
- 元データのSHA-256:
  `e41b8cd30eddb170bfa1af8c871a27684dc59aa7fbcad54a50e86f0f794af76f`。
- 確認用プログラムをCMに書込み、`picotool load -v`で照合してから再起動。
  COM9に復帰し、5秒間の受信で6件の正しいJSONを取得。
- 全6件ともGPIO13/D+=1、GPIO12/D−=0。
  オス端子は空けるよう依頼した構成。デジタル値のみで、電圧・抵抗値の測定ではない。
- D+がHighという結果は回路図の1.5kΩプルアップと整合するが、
  当時は実物の抵抗配置・値・電源経路は未測定。後続の手動測定は末尾に記録。

記録: `analysis/cm-original-backup.json`、`analysis/cm-input-check.json`。
受信の詳細は`local/cm-input-check.json`、ビルド記録は`artifacts/cm-input-check/manifest.json`。
これは**補助ボードのバックアップと通信確認**。T3P本体のバックアップやROM接続成功ではない。

UF2検査では実データをRP2350 Secure Arm、連続した2MiB内のFlash領域に限定する。
公式picotoolが先頭に付けるRP2350-E10対策レコードは、IGNORE拡張と既知の全内容を照合して
別扱いにする。異なるチップ・Flash範囲・ブロック欠落・IGNORE破損を拒否する検査も実施した。
実データの範囲は`0x10000000`〜`0x1000d200`未満。

## 入力検査後の接続条件と、その後の進展

CMはまだT3Pへつながない。USB_KEYの応答判定では出力を解放した後の線の状態を使うため、
常時D+をHighへ引く抵抗の影響を無視できない。実物を確認し、必要なら抵抗の変更か
RP2350B-Plus-W＋別のUSB配線へ変更する。R10の確認・取り外し手順は末尾を参照。

通常USBホスト用の終端、CC、VBUS給電と逆流も合わせて構成を決める。
後続の実験でPIOホストと通常HIDの固定読取りは成功した。
[CM経由の通信記録](CM_USB_BRIDGE.ja.md)を参照。
USB_KEYによるT3P ROM接続・全Flashバックアップは未達。

## 商品画像からの部品確認

ユーザー提供の商品画像では、下端のCC表示と説明番号3はCC用の抵抗設定。
D+プルアップのR10とは区別する。番号3を手掛かりに取り外さない。

`USB-CM`文字のすぐ右には黒い2端子部品が横に3個並んでおり、
データ線用抵抗群の候補として調べる。ただし商品写真には部品番号がなく、
この3個のどれがR10かは未確定。写真だけで左・中央・右をR10等と命名しない。

実物が同じ配置なら、CMを全てのUSB・電源から外して抵抗レンジで各部品の
両端を測り、左・中央・右の値を記録する。実装状態では他の回路の影響を受けるため、
1.5kΩらしい値だけで取り外しを決めず、実物写真と3V3/D+への接続確認を合わせる。
この段階は測定のみで、取り外し箇所の確定ではない。

### 実物写真とユーザーの抵抗測定

実物の表裏写真を受領。裏面にWaveshareとRP2350-USB-CMの印字があり、
表の対象3個も商品写真と同じ位置に確認できる。
表側、メス端子を上・オス端子を下にした向きで、`USB-CM`文字のすぐ右の
3個を左からA/B/Cと呼ぶ。B/CのどちらがR11/R12かは未確定。

| 位置 | ユーザー報告値（基板上で測定） |
| --- | --- |
| A（左） | 1.510kΩ = 1510Ω。最初のΩ表記をユーザーがkΩへ訂正 |
| B（中央） | 約28Ω |
| C（右） | 約28Ω |

値の組合せは回路図のR10=1.5kΩとR11/R12=27Ωに整合する。
AをR10の有力候補とし、追加のユーザー測定で次を確認した。
3V3端子はこの向きで左上の5V/GNDの次の金色の穴。

| 測定箇所 | ユーザー報告値 |
| --- | --- |
| 3V3穴 - A上端 | 1.51kΩ |
| 3V3穴 - A下端 | 0.200Ω |

A下端は3V3へ直結し、上端まで1.5kΩとなる。
実物の配置、3個の抵抗値、3V3への接続、初回GPIO13 Highという結果を合わせ、
Aを回路図のR10と判断した。GPIO13からA上端への直接導通は未測定であり、
部品番号の判断とその測定実施は区別する。

### 抵抗の取り外し

全USB・電源を外したまま、Aだけを取り外す。B/CとCCの部品は残す。
両端のはんだが溶けた状態で外し、片端が固いまま引っ張ったり、基板をこじらない。
外した部品は保管する。取り外し後は両パッドがはんだでつながっていないことと、
隣のB/Cが動いていないことを写真で確認してから、PC単独の再試験へ進む。
この作業だけでUSB_KEYやPIOホストの電気条件が全て整うとはしていない。
T3Pはまだ接続しない。

2026-11-01、ユーザーからAを取り外したとの報告。顕微鏡でショートが見られないことを
確認し、取り外した抵抗は保管している。取り外し後の写真は未受領。
ユーザーの目視確認と、次の電気的な入力検査を区別して記録する。
元のFlashバックアップは引き続き保持するが、ファームの復元だけで外部抵抗は戻らない。
今回の補助用途ではAを外した構成で進め、再取付けを現手順の条件にはしていない。

## 取り外し後の入力検査（v2、2026-11-01）

CMのメス端子だけをPCへ接続し、オスは空けるよう依頼。ユーザーが接続完了を報告。
まず既存v1をCOM9で3秒間受信し、4件ともD+=0、D−=0。
内蔵プル無効時の浮いた入力であり、このLowだけを取り外し成功の根拠にはしない。

v2を別ディレクトリー`artifacts/cm-input-check-v2`に生成し、Flash書込み照合後に再起動した。
v1のUF2・マニフェストと元の全Flash保存はそのまま保持。
v2は通常時に内蔵プルを無効にし、明示的な`PULLCHECK`コマンドで次だけを行う。
GPIO12/13の出力ドライバーは無効のまま、弱い内蔵プルの組合せを変え、各5ms待って報告。

| 内蔵プル設定 | 期待するD+ / D− | 実機結果 |
| --- | --- | --- |
| 両方Down | 0 / 0 | 3回とも一致 |
| 両方Up | 1 / 1 | 3回とも一致 |
| D+ Down、D− Up | 0 / 1 | 3回とも一致 |
| D+ Up、D− Down | 1 / 0 | 3回とも一致 |
| 両方無効へ戻す | 浮くため値を規定しない | 3回とも無効へ復帰した報告を受信 |

3サイクル、4種類の有効なプル設定で12検査すべて合格。解放後を含む15件の記録を取得。
今回のデジタル検査では、強いHigh固定やD+/D−間の直結短絡を示す結果は見られない。
3.3Vの実測・信号波形・27Ω抵抗からUSBコネクターまでの導通、USB通信品質までの証明ではない。
内蔵プルはUSBホスト用15kΩ終端の代用とみなさない。

`scripts/cm_input_commands.py`は実機のVID/PIDと診断のボード・版・GPIOプロフィールを
受信確認してから、固定の`BOOTSEL`または`PULLCHECK`だけを送信する。
PULLCHECKはv2専用、初期状態はプル無効を要求。不一致・短い送信・フェーズ欠落は停止する。
PC側の6件の偽通信テストと、v2 UF2の4件の破損・対象検査は合格。
ボードへのBOOTSEL指示と復帰も実機で確認した。

証拠は`analysis/cm-after-removal.json`、生の受信は`local/cm-pull-check-after-removal.json`。
この入力検査の直後はv2が動作し、内蔵プルは無効、T3P未接続だった。
その後[通常HIDの通信](CM_USB_BRIDGE.ja.md)まで成功し、
現在は[スコープ確認](CM_WAVE_SCOPE.ja.md)用プログラムを入力待機させている。
