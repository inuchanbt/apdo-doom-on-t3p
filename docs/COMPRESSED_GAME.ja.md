# ゲームデータの圧縮と部分読取り

既存のFreedoom E1M1変換データを変更せず、4KiBごとに独立したraw DEFLATEで圧縮する。
小さくならないページは元のバイト列を保存する。全体を展開する必要はなく、
`native/t3p_game.c`が4KiB×8のキャッシュへ必要なページを読み出す。
物理Flashからの読取りはまだ試していない。

| 項目 | 結果 |
| --- | ---: |
| 元データ | 2,802,000バイト |
| 圧縮後・索引込み | 1,189,607バイト |
| ページ数 | 685 |
| 圧縮後の割合 | 42.46% |
| PC用ABIでの読取り状態・キャッシュ | 32,872バイト |

元データSHA-256は`6b25a4f1adb6f1f1f5f42226c272b93ccff4f356ac8d7034cf83712b2da70c08`、
圧縮後は`3247cfe10f0d01ac54d5f1ffb4f92485cf449151b0d9e445f8f0e5df72e3d846`。
入力・出力ファイルを含む詳細は`artifacts/game/E1M1.json`。

展開ライブラリはJoergen Ibsenの[tinf](https://github.com/jibsen/tinf)、zlibライセンス。
ソース・ライセンス・リビジョンを`vendor/tinf`に保存した。ネイティブビルドでは内部整合性の
assertだけを無効にし、入力・出力範囲のエラー検査は維持する。

```powershell
& 'D:\KM003C\.venv\Scripts\python.exe' scripts\pack_game.py
& 'D:\KM003C\.venv\Scripts\python.exe' scripts\check_game_pack.py
```

Python側で元データ全体への復元一致を確認。C側でも全685ページ、5,000か所のランダム読取り、
ページをまたぐ読取り、末尾、不正範囲、欠損ファイル、索引／データ破損を検査した。
さらに同じ読取り処理をWindows用DOOMに接続し、E1M1を実際に起動・描画した。

T3PGAME1形式は以下のlittle-endian固定配置。将来変更する場合はversionを上げる。

| オフセット | 内容 |
| --- | --- |
| 0 | 8バイトのASCII `T3PGAME1` |
| 8 | u32 version=1 |
| 12 | u32 元データ長 |
| 16 | u32 ページサイズ=4096 |
| 20 | u32 ページ数 |
| 24 | u32 パッケージ全長 |
| 28 | u32 索引のCRC32 |
| 32 | 元データのSHA-256、32バイト |
| 64 | 各16バイトの索引: u32保存位置、u32保存長＋最上位bitは非圧縮、u32復元長、u32復元CRC32 |
| 索引直後 | ページの保存データ、隙間なし |

読取り開始時にヘッダー・索引・各ページ範囲を検査し、展開時に復元長とページCRC32を確認する。
SHA-256の全体比較はホスト検査で行う。マウント中に入力イメージが変化しないことが前提。
破損時には読取りエラーを返す。複数ページの読取り失敗では出力の一部が既に書かれ得るので、
ゲーム側はエラー後に処理を止める契約。

これまでのKM003Cの変換元・生成コードを引き継ぐ。FreedoomのBSDライセンスと、
含まれるエンジン文字列・テーブルのGPLを維持する。配布用の完成ファームではなく、
ローカルのゲーム資産。生成先にゲームとエンジンの告知を同梱する。
