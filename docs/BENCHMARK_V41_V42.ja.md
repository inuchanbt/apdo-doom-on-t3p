# V41 / V42：DEFLATE内部の時間配分を測る

2026-11-05作成・実機比較完了。**両版が同じ画像列で完走。展開本体が主要な負荷と判明した。**
V39/V40は約666〜668 ms／フレーム、うち展開425〜430 msで、
内側2関数のSRAM実行に速度優位は見られなかった。
今回は高速化版ではなく、その約425 msの内訳を調べる計測版。

## 共通条件と変更

V37/V39とバイト単位で同じ従来パック（1,249,137 B）、2 KiBページ35枚、
8枚のフラット・32本の描画カラムのキャッシュ、120×120の8ビット画面を維持。
10フレーム準備＋30フレーム測定、1フレーム1 tic、入力無効。
V39の7ビット検索表・長い符号の継続方式を使い、解凍コードは両版ともFlashで動く。
CPU／PLL／SFCやキャッシュの設定、LCDの分周値は変更していない。

- **V41**：動的ヘッダーの読取り＋符号の木の準備、圧縮データ本体、
  storedブロックを大きな区間で計時。解凍・ブロック・符号・追加ビットの呼出し数も数える。
  符号と追加ビットのヘルパー内では時計を読まない。
- **V42**：V41と同じ集計に加え、符号と追加ビットのヘルパーをそれぞれ
  64回に1回だけ計時する。最初の呼出しも対象。空の時計読取り区間も記録する。
- ページ順位表示と旧ページ別累積時間を外した。表示していなかったキャッシュカウンターの
  レジスター読取りと起動時クロック設定のスナップショットも両版で省略。
  空いた領域を計測コードに使い、Flashドライバー80 KiB・RAMドライバー32 KiB・
  スタック16 KiBの予約は維持した。
- フレーム11の直前に集計だけをリセットする。ページ／アセットキャッシュとCRC確認状態は残す。
  リセットと画像列ハッシュの計算はフレーム時間の測定外。

## 読み方と制約

既存TIMER0の生カウンターを使う。BSPと同じ24 MHz÷4096の前提で、
1 tick = 64/375 ms ≈ 170.7 µs。新たな周波数の実測校正は行っていない。
15〜17行を1フレーム当たりに換算する式は `tick × 64 / (375 × 30)` ms。
各計時区間は16ビットの1周（約11.18秒）未満である必要がある。

**23／26行は15／16行に内包される。足し合わせない。**
`getbits_base` は生の全ビット読取りを表すものではなく、追加ビットを読んで基準値を足す
ヘルパーだけの範囲。ビット数0の呼出しも計数する。
V42の標本tickを64倍する値は参考推定で、正確な関数別の総時間ではない。
短い処理は1 tick未満になり、決まった64回間隔は処理パターンと同期して偏る可能性がある。

28行の空区間は時計呼出し間の一部負担を見るためのもの。
カウンター更新・分岐・レジスター退避など**計測負担の全部は含まない**ため、
これを機械的に引いて補正しない。V41/V42のフレーム・展開時間の差も確認する。
両版とも計測と配置の影響があるので、V39や通常版からの速度改善を示す比較には使わない。

まずV41で木の準備が大きいか、展開本体が大きいかを判断する。
V42の標本が十分な分解能と数を持つ場合に、符号／追加ビットの比率を補助材料にする。
不足する場合はそこから細かい順位を断定しない。

## 実機結果：2026-11-05

ユーザーが両版の最終画面を撮影。最初の「V29/V30」という説明は
「V41/V42」に訂正され、先頭行も `29` / `2A` で一致。
両版とも30フレーム・D00E・最終40 tic・画像列ハッシュ `C269CBCE` を確認した。
各版1回の入力なし開始地点の試験であり、通常プレイや長時間の安定性は含まない。

| 区間（ms） | V41：平均／最短／最長 | V42：平均／最短／最長 |
|---|---:|---:|
| フレーム全体 | 729／699／804 | 822／818／946 |
| 外側の展開計時 | 489／459／554 | 614／578／650 |
| LCD送信 | 83／83／84 | 83／83／84 |

| DEFLATE内の区間 | V41：累積tick／1フレーム換算ms | V42：同左 |
|---|---:|---:|
| 木の準備・ヘッダー | 16,743／95.25 | 18,822／107.08 |
| 展開本体 | 67,129／381.89 | 86,026／489.39 |
| stored | 0／0 | 0／0 |

V41では展開本体が粗い2区間合計の約80％。外側の展開489 msに対しても約78％を占める。
区間境界・計測処理・各呼出しのms量子化があるため、内側の合計と外側の値は厳密には一致しない。
木の構築だけを改善しても全負荷の大半は残るので、次は展開本体のループを対象とする。

両版で呼出し数も一致：解凍3,074回、dynamic 3,074ブロック、fixed/stored 0。
符号読取り3,745,007回、`getbits_base` 1,311,797回。
V42の標本数58,516／20,497はそれぞれ呼出し数の1/64（切上げ）と一致し、
空区間79,013回は両標本数の合計と一致した。

V42の標本tickは符号4,773、追加ビット819、空区間914。
**符号標本を単純に64倍すると約1,738 ms／フレームとなり、外側の展開614 msを超える。**
この推定を実処理の時間や占有率には使えない。
短い関数に対して時計・呼出し・退避などの負担、粗い量子化、決まった間隔での標本抽出が効いている。
空区間の差引きだけで解消した値としても扱わない。
V41/V42自体もV39より計測負担があり、性能の退行や高速化を示す比較にはしない。

写真を拡大して手動転記した全30行・写真SHA-256・換算値を
`analysis/native-doom-v41-v42-benchmark.json` に保存。写真本体は配布しない。
次のV43/V44では詳細計測を外し、従来デコーダーと短いリテラルの連続処理を比較する。
