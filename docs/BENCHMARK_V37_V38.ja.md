# V37 / V38：ページ別の累積展開時間

V37はV33と同じ従来パック、V38はV34と同じ混在パック。
10フレーム準備後、入力なし・描画1回につきゲーム1 ticという同じ条件で
30フレームを測定し、最後に停止する。今回は展開の重い上位8ページを残す。

## 操作

1. V37を書き込み、ボタンを押さずに通常起動する。
2. 3行目が `0000D00E` になって停止したら数秒待ち、左上の**全30行**を撮る。
3. V38も同じ手順で撮る。

ボタン無効・最後の停止は仕様。通常プレイはV30またはV32へ戻す。
書込み用は各版の `T3P_NATIVE_DOOM_...bin` で、`DO-NOT-FLASH` は使わない。

## 上14行

1行目はV37=`00000025`、V38=`00000026`。
2行目は測定回数 `0000001E`（30）、3行目は完了 `0000D00E`。
4〜6行はフレーム時間、7〜9行は展開時間、10〜12行は送信区間の
平均・最短・最長（すべて16進数、ms）。13行目の最終ticは `00000028`（40）、
14行目の画像列照合値は `C269CBCE` を想定する。実機で一致を確認する。

## 15〜30行：上位8ページ

順位ごとに2行使う。1位は15・16行、2位は17・18行、8位は29・30行。

| 行 | 上4桁 | 下4桁 |
|---|---|---|
| 順位の1行目 | ページ番号 | 30フレーム分の累積展開時間（ms） |
| 順位の2行目 | 保存方式：`0001`＝DEFLATE、`0002`＝LZ4 | 30フレーム分の展開回数 |

たとえば `053503E8` → `00010014` は、ページ `0x535` をDEFLATEで
20回展開し、合計1,000 ms使った、という意味。
そのページだけで平均約33 ms／フレームに相当する。
該当するページが8枚未満なら、余った順位は2行とも0。

順位は累積時間が長い順。同時間なら展開回数が多い順、それも同じなら
ページ番号が小さい順。ページの追加保存容量を加味した順位ではない。
圧縮サイズはPC上の同じパックから調べ、次の変更対象を決める。

## 集計の範囲

- 起動と10フレームの準備は集計から除外する。11フレーム目の前に、
  ページ別の時間・回数だけをリセットする。ページキャッシュや初回CRC確認の
  状態は保持するので、準備済みのキャッシュを使う条件は維持される。
- キャッシュに命中してコピーするだけなら展開回数は増えない。
  追い出したページを読み直して再展開すると時間・回数に累積する。
- 無圧縮ページは直接読めるため、この展開順位には入らない。
- 既存の展開タイマーを使い、V35／V36の細かいコピー・フェーズ計測は外した。
  毎フレームの並べ替えは行わず、最後の測定後に順位を作る。
- ページごとの時間・回数はそれぞれ16ビットで、65,535を超えると飽和する。
  `FFFF` はその値以上という意味で、巻き戻って小さな値にはならない。
- 今回のE1M1全1,369ページに合わせて集計表を確保。パックがその容量を
  超えれば、読み始める前に拒否する。ページキャッシュは従来どおり35枚。
- 集計の追加とRAM・コード配置の変化がある。以前の版との差をそのまま
  性能向上率とはしない。入力なしの開始地点に関する結果で、移動や発射時の
  負荷は別に確認する。画像照合値はFNV-1aで、暗号学的な一致証明ではない。

## PC検査

両パックで全1,369ページ・5,000件のランダム読取り・破損と範囲外を検査。
擬似時計を使い、キャッシュ命中と再展開の区別、キャッシュを保持した集計リセット、
累積、飽和、上位8件と同順位の扱い、結果を表示しても集計を壊さないことを確認。

```
python scripts/check_game_pack.py --page-totals --packed artifacts/native-doom-v37/E1M1-2k.t3pg
python scripts/check_game_pack.py --page-totals --lz4 --packed artifacts/native-doom-v38/E1M1-2k.t3pg
```

66件の回帰テストと、実エンジンの40フレーム＝40 tic検査も通過。
別の展開ツールで書込みファイルを読み直し、app.binがビルドした内容と一致し、
純正3.0.3のその他46エントリーが同じことを確認した。
従来の80 KiBのドライバーFlash予約、32 KiBのRAM予約、16 KiBのスタック予約を維持。
予約込みのFlash余裕はV37が188 B、V38が1,712 B、RAM余裕は両方1,760 B。
実機での完走と照合値は下記のとおり確認済み。

## 実機結果：2026-11-05

ユーザーによる書込み・撮影。画像同期の遅れで先に届いた別版の写真を除外し、
先頭行が `25`／`26` の訂正版を使用した。各版1回、準備10＋測定30フレーム。
両版とも完了 `D00E`、最終tic `28`、画像列照合値 `C269CBCE` が一致した。
最後の停止と入力無効はこの計測版の仕様で、通常プレイ中のフリーズではない。

| 区間（ms） | V37 従来：平均／最短／最長 | V38 混在：平均／最短／最長 |
|---|---:|---:|
| フレーム全体 | 668／639／735 | 686／648／751 |
| 圧縮ページ展開 | 428／400／482 | 444／423／500 |
| LCD送信区間 | 83／83／84 | 83／83／84 |

平均から換算すると約1.50／1.46 fps。この1組では混在版が18 ms長く、
速度優位は確認できなかった。反復測定がないため、有意な退行の断定もしない。
展開は全体の約64％。以前の版とは計測と配置が違うので、直接の改善率にはしない。

| 1 | `544`／359／60 | `228`／453／120 |
| 2 | `525`／342／60 | `557`／426／60 |
| 3 | `538`／329／60 | `227`／352／90 |

ページ番号は16進、時間と回数は10進。全16件ともDEFLATEで、パックの方式フラグとも
照合済み。写真を拡大して読み取った値であり、本体から取得した数値ログではない。
写真SHA-256、全30行の転記、各ページの保存サイズを
`analysis/native-doom-v37-v38-benchmark.json` に保存した。写真・ゲーム素材は含めない。

上位8枚の合計は2,521／2,720 ms、1フレームあたり約84／91 ms。
展開428／444 msの大部分はそれ以外のページで発生している。
従来版の上位 `544`・`538`・`537` は混在版でLZ4になり順位から消えたが、
別のDEFLATEページが上位を占め、全体の展開時間は減っていない。
これはキャッシュ競合などを調べる材料になるが、順位だけで原因は確定できない。

次の比較基準は従来パックとし、少数ページの方式入替えに加えて、全DEFLATEページに
効く展開ループや命令読取りの改善を検討する。今回の結果記録では次版を生成していない。
