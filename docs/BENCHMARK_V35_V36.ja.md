# V35 / V36：残る処理時間の内訳

V35はV33と同じ従来パック、V36はV34と同じ混在パック。
ゲームデータ・キャッシュ35枚・描画・DBI・クロック設定は共通で、
計測箇所だけを増やした。性能改善版ではなく原因を絞る診断版。

## 操作

1. V35を書き込み、ボタンを押さずに通常起動する。
2. 10フレームの準備と30フレームの測定が終わり、3行目が
   `0000D00E` になって停止したら、数秒待って左上の**全30行**を撮る。
3. V36も同じ手順で撮る。余裕があれば各版を再起動して複数回測る。

ボタンが効かず、最後に停止するのは仕様。通常プレイへ戻す場合は
V30またはV32を使う。書込み用は各版の `T3P_NATIVE_DOOM_...bin`。
`DO-NOT-FLASH` ファイルは使わない。

## 表示行

16進表記。時間はms。1行目のリビジョンはV35=`23`、V36=`24`。

| 行 | 内容 |
|---|---|
| 1〜3 | リビジョン／測定回数 `1E`（30）／完了 `D00E` |
| 4〜6 | フレーム時間の平均／最短／最長 |
| 7〜9 | DEFLATE＋LZ4展開時間の平均／最短／最長 |
| 10〜12 | 最初の帯の送信から最後のDMA完了までの平均／最短／最長 |
| 13〜14 | 最終ゲームtic（予定 `28`＝40）／画像列照合値（予定 `C269CBCE`） |
| 15 | 圧縮ページのFlash→SRAM読取り：平均ms |
| 16 | 無圧縮ページのFlash→要求先コピー：平均ms |
| 17 | 展開済みページキャッシュ→要求先コピー：平均ms |
| 18 | ページの初回CRC確認：平均ms |
| 19 | アセット読取り全体（上記の処理やキャッシュ検索を含む）：平均ms |
| 20 | 入力とゲーム進行処理（その間の読取りを含む）：平均ms |
| 21 | 音声状態更新＋画面描画（その間の読取りを含む）：平均ms |
| 22 | 色変換・拡大からDMA完了までの送信関数全体：平均ms |
| 23 | フレーム全体から20〜22行の区間を除いた残り：平均ms |
| 24〜25 | DEFLATEのみ／LZ4のみの展開：平均ms |
| 26 | 無圧縮Flashコピーの総バイト数（測定30回の合計） |
| 27 | 圧縮Flash読取りの総バイト数（同上） |
| 28 | 展開済みページからのコピー総バイト数（同上） |
| 29〜30 | DEFLATE／LZ4の総展開回数（同上） |

26〜30行は平均ではなく合計。V35のLZ4時間・回数は0を想定。
同じパックなら、追加したタイマーでゲームの進行は変わらないため、
13〜14行はV33／V34と一致する見込み。実機で確認する。

## 読み取り上の注意

- 19〜21行は内側の読取りや展開も含む。15〜25行を全部足すと二重計上になる。
- 画面描画の数値は純粋な描画計算だけの時間ではない。S_UpdateSoundsと
  D_Displayの区間を測り、必要なアセット読取りも含める。
- 17行はページキャッシュからのコピー。上位のアセットキャッシュや
  エンジンの4 KiBキャッシュ内のコピーは19行または21行に含まれる。
- 1 ms単位の時計なので、短いコピーを何度も測ると丸め誤差が積み重なる。
  追加タイマーの負担もフレーム時間に入る。V35とV36を対で比べ、
  V33／V34の絶対時間とは直接比較しない。
- 初回CRCは起動から一度しか検査しない。準備後に新しいページを使わなければ
  18行が0になるのは正常。ゲームパックのCRC確認は無効化していない。

## PCでの確認

両パックで全1,369ページ・5,000件のランダム読取り・範囲外と破損を検査。
擬似時計により、無圧縮直読、展開済みキャッシュ、初回CRC、圧縮読取り、
DEFLATE／LZ4の区別、再オープン時のカウンター初期化も検査した。

```
python scripts/check_game_pack.py --breakdown --packed artifacts/native-doom-v35/E1M1-2k.t3pg
python scripts/check_game_pack.py --breakdown --lz4 --packed artifacts/native-doom-v36/E1M1-2k.t3pg
```

生成ファイルを別の展開ツールで読み直し、app.binがビルドした内容と一致し、
純正3.0.3のその他46エントリーが同一であることを確認した。
従来と同じ80 KiBのドライバーFlash予約、32 KiBのRAM予約、16 KiBの
スタック予約を維持。予約込みのFlash余裕はV35が92 B、V36が1,568 B、
RAM余裕は両方2,960 B。これはオフライン配置確認値。実機の計測完了は下記を参照。

## 実機結果（2026-11-05）

両方とも測定30回、最終tic40、画像列照合値 `C269CBCE` で一致。
V35の写真は283×377 pxのため、拡大して読めた時間の行を採用した。
下部の総バイト数・展開回数は転記を保留し、以下の判断には使用していない。

| 平均時間（ms） | V35：従来 | V36：混在 |
|---|---:|---:|
| 全フレーム | 676 | 693 |
| 全展開 | 428 | 444 |
| 圧縮Flash読取り | 17 | 20 |
| 無圧縮Flashコピー | 2 | 2 |
| ページキャッシュからのコピー | 6 | 6 |
| 初回CRC | 0 | 0 |
| アセット読取り全体（内側を含む） | 489 | 496 |
| 入力・ゲーム進行（内側を含む） | 21 | 21 |
| 描画区間（内側を含む） | 570 | 587 |
| 送信関数全体 | 84 | 84 |
| 最初の帯〜DMA完了 | 83 | 83 |
| DEFLATEのみ | 428 | 432 |
| LZ4のみ | 0 | 11 |

V36は平均17 ms（2.5%）遅かった。展開が全体の約63〜64%を占め、
直接FlashコピーやCRCは主要な負荷ではない。各区間の平均は整数切捨てのため、
432＋11と全展開444のように、内訳の合計と1 msずれることがある。

前回V33／V34の混在方式の小幅な優位は、この追加計測では再現しなかった。
追加タイマーやコード配置の影響を分離していないので、絶対時間から計測負担を
算出したり、混在方式が常に遅いと結論づけたりはしない。
通常プレイの基準版はV30を維持。次は測定30回のページ別累積展開時間と頻度を
集め、LZ4化やキャッシュ保持の対象を選び直す。

ファームのSHA-256を記録した。写真原本はリポジトリに含めない。
