# CM単独での復旧キー候補波形の確認

2026-11-01。ユーザーはRIGOL MHO984（ロジアナ付き）とUSB-Cメスの端子取り出し基板を所有。
まずT3Pを外した状態で、候補波形を観測する準備を進める。
T3PへのUSB_KEY送信・ROMモード接続はまだ実施していない。

## 接続を依頼した構成

```text
PC ── CMのメス
      CMのオス ── USB-Cメス端子取り出し基板
                    D− ── MHO984 CH1の先端
                    D+ ── MHO984 CH2の先端
                   GND ── 両プローブのGND
```

T3Pは接続しない。端子取り出し基板のVBUS/5Vへは測定用の線を追加しない。
通常の受動プローブを使用し、プローブ倍率と本体設定はともに10倍、DC結合、入力1MΩ。
MHO900の[公式取扱説明書](https://www.rigol.com/dam/global/downloads/brochures/en/user-manual/oscillosopes/MHO900_UserGuide_EN.pdf)
5.6節で1MΩ/50Ω切替を確認した。今回は50Ωにしない。
ユーザーから接続・設定完了の報告を受けた。

観測開始の設定案:

- CH1/CH2とも1V/div。
- 時間軸50µs/div、トリガー位置20〜25%程度。
- エッジトリガー、CH1の立上り、レベル約1.5V。
- サンプルレート100MSa/s以上を確保。SINGLEで待機してからPCで一回だけ送る。
- 最初の記録で全16クロックを確認し、必要な場合だけ拡大してデータのセットアップを調べる。

## スコープ専用プログラム

`recovery/cm_wave_scope`、出力は`artifacts/cm-wave-scope/RP2350_CM_WAVE_SCOPE_BENCH_ONLY.uf2`。
起動時はGPIO12/13を入力・弱いプルダウンにし、PIOの出力許可は0。
`SCOPE_KEY_ONCE`コマンドで候補フレームを一回だけ出し、自動では繰り返さない。
USBホスト、T3P向けUSB要求、ACK検出、RAMローダー、Flash操作はない。

| 項目 | 候補設定 |
| --- | --- |
| クロック | D− / GPIO12 |
| データ | D+ / GPIO13 |
| データ順 | `0x16EF`をMSBから`0001011011101111` |
| CMシステムクロック | 120MHz、PIO分周1 |
| クロックHigh | 1,160サイクル = 約9.6667µs |
| クロックLow | 1,155サイクル = 9.625µs |
| 次ビットのデータ設定 | クロック立上りの15サイクル前 = 125ns |
| 最終立下り後の出力解除 | PIO命令上3サイクル後 = 25ns |

キー値・ビット順は公式SDKのBR35参照ROMの解析と整合する。
時間設定は先行研究の候補であり、T3Pで測定したROM受信条件ではない。
最初の出力更新から最後の立下りまではモデル上37,040サイクル、約308.667µs。

DMAで48個の制御ワードをPIOへ送り、最後のワードを読むとPIO自身が出力許可を解除してIRQを立てる。
CPUがUSB割込み等で遅れても、この解除をCPU処理待ちにしない。
PIOのFIFO欠乏フラグ、20msの期限、解除後の出力許可も検査し、異常は送信禁止状態にする。
CPU側でも冗長に出力許可を解除する。
弱いプルダウンは解除後も残り、出力解除後のアナログ電圧の減衰は容量と抵抗に依存する。
電圧が落ちる時刻だけから25nsの出力解除を直接測定したとは扱わない。

両入力が弱いプルダウンでもHighなら送信を拒否する。これは接続確認の補助であり、
T3Pが外れていることを物理的に保証する検出器ではない。

## 済んだ検査と現在位置

- ビルドは警告なし、UF2対象・範囲・破損検査4件合格。
- 実際のCコードで生成した48ワードを、アセンブル済みPIO命令のサイクルモデルで実行。
  全16ビット、High/Low周期、データ設定、最後の入力への切替とIRQの順序が一致。
- PC側の送信前プロフィール検査・High入力拒否・異常時非再送の4件合格。
- CMへ書込み照合して起動。実機の状態報告でPIO出力許可0、送出回数0、故障なしを確認。
- 接続・設定完了のユーザー報告後、`SCOPE_KEY_ONCE`を一度だけ送信。
  CMは完了・FIFO欠乏なし・PIO出力許可0・送信回数1を報告。
- 追加送信しない状態受信でも、出力許可0、送信回数1、故障なしを再確認した。
- この初回時点では全波形は未取得だった。後続のLAN取得と実測結果を末尾に記録。

`analysis/cm-wave-timing-model.json`はソフトウェア上の計算結果。
パッド電圧、実際のエッジ、DMAの競合、T3P ROMの動作まで確認したものではない。
PCツールは`scripts/cm_wave_scope.py`。既定では状態受信のみ、`--emit`で固定フレーム一回。

最初の送信記録は`local/cm-wave-scope-first.json`、追加送信なしの状態確認は
`local/cm-wave-scope-after-first.json`。次は停止画面または保存波形を受領して検査する。
波形が一致してからT3Pの起動時の応答・USBホストへの切替を別工程で検討する。

## SINGLE待機の訂正と2回目の送信

ユーザーから初回はSINGLE待機になっていなかったとの訂正と、今SINGLEにしたとの報告を受領。

## 初回画像の確認とLAN経由の取得

ユーザーから停止画面を受領し、無加工の原本を`local/scope-captures/frame2-screen.png`に保存。
表示は時間軸2.90µs/div、500MSa/s、10k点、CH1=50mV/div、CH2=100mV/div、
トリガーレベル約14.46mVだった。記録時間は20µsで、全16ビットを収められない。

ユーザーが指定したLANアドレスでRIGOL MHO984を機種照合し、TCP5555のSCPIへ接続。
既存の停止波形をASCII電圧として保存してから、入力・取得設定を変更した。
CH1は既存記録の量子化上限に達する点があり、この画面だけから低振幅や接触不良を確定しない。

その後の共通取得条件は次のとおり。

- 1M点、100µs/div、中央トリガー。実際の取得は1GSa/s、1ns間隔、1ms記録。
- CH1/CH2とも1V/div、DC結合、1MΩ、倍率10。表示位置は分離するため調整。
- CH1立上り1.5V、SINGLE。SCPIでWAITを確認してから、CMへ一回だけ送信。
- STOPを確認後、両チャネルの全1M点をWORD形式で保存。
  先頭32点を計測器自身のASCII電圧と比較し、バイト順・換算式を照合。
- 以後の比較でも入力と時間軸の設定を読み返し、同じ設定であることを照合した。

操作は`scripts/mho984_scope.py`。工場初期化、信号発生器、スコープの更新は操作しない。
公式[Programming Guide](https://www.rigol.com/dam/global/downloads/brochures/en/program-guide/oscilloscopes/MHO900-ProgrammingGuide.pdf)
に従い、`EDGE`など必要な表記を使用した。ユーザー指定IPと機器固有情報は`local`だけに保持。

## 全波形と接地・駆動設定の比較

第3回は元のGND配線。第4回はユーザーが追加の20cm GND延長を省いた構成。
第5回は同じ短縮構成でGPIOを明示的に2mA駆動・低速スルーへ設定した。
3回ともPIO命令と48ワードのデータ生成は同一。各回は個別に指示した一回の送信で、
T3Pは外したまま。スコープの自動反復取得やCMの自動再送はしない。

全3記録とも次を満たした。

- 立上り16回、立下り16回。データを1.65Vで判別すると`0001011011101111` = `0x16EF`。
- クロックHigh 9.666〜9.667µs、Low 9.625〜9.626µs。
- 値が変わる7ビットではデータがクロックより125〜126ns先行。
  クロックの50ns前と1µs後でも各ビットの判定が同じ。
- 平坦部はクロックHigh約3.29V／Low約−0.01V、データHigh約3.34V／Low約0.04V。
- ADCの上限・下限でのクリップなし。

測定されたエッジ近傍の最大・最小値:

| 条件 | CH1最大 / 最小 | CH2最大 / 最小 |
| --- | --- | --- |
| 第3回・GND延長あり | 4.228V / −1.061V | 3.742V / −0.492V |
| 第4回・追加GND延長なし | 4.144V / −0.930V | 3.593V / −0.296V |
| 第5回・追加延長なし、2mA設定 | 4.036V / −0.840V | 3.534V / −0.225V |

測定されたピークはいくらか減ったが、プローブ付属のGNDワニ口線は残る。
無負荷の取り出し基板・測定配線も含む値であり、CM端子そのものの真のピークや、
T3Pを接続した負荷条件の電圧と同一とは扱わない。帯域制限でピークを隠していない。

最新の全体図は`artifacts/cm-wave-scope/measured-frame5.png`、
エッジ拡大は`artifacts/cm-wave-scope/measured-frame5-edge.png`。
解析は`scripts/analyze_cm_scope.py --frame 5`で再現する。
閾値交差を平滑化して作り直す処理はせず、余分なクロック交差があれば停止する。

## PIO自身の出力解除の確認

スコープ用v2から、完了IRQ後・CPUによる冗長な解除より前にPIOの出力許可を読み取るようにした。
第4・5回とも`pio_oe_before_cpu_release=0`、CPU解除後も0、FIFO欠乏なし、故障なし。
これはPIOがCPUの補助を待たずに解除済みであることの読取り結果。
25nsという時刻そのものの外部実測ではない。D+の電圧が閾値を下回るまでには
最後のクロック立下り後約0.76〜0.79µsあり、弱いプルダウンと容量による減衰を含む。

現在のCMはスコープ用v3、2mA・低速スルー設定を読み返して確認済み。
`artifacts/cm-wave-scope-v3/RP2350_CM_WAVE_SCOPE_BENCH_ONLY.uf2`を照合書込みした。
v1/v2のUF2と各ソースは別フォルダーへ保持している。
v3での送信後も出力許可0・入力待機を受信確認した。
スコープは第5回を保持してSTOP、CMは追加送信しない。

集約は`analysis/cm-wave-scope-state.json`、各全波形解析は
`analysis/cm-wave-physical-frame3.json`〜`frame5.json`。
生波形は`local/scope-captures/frame3-raw`〜`frame5-raw`。

**設定したビット列と時間幅の実測は一致。T3PのROMで受信されたという確認ではない。**
次はT3Pを接続した応答観測の配線を決めるため、取り出し基板の端子構成を確認する。

## 追加の中継取り出し基板（写真確認、未測定）

2026-11-01、ユーザーからUSB-Cオス・メスと2列ヘッダーを持つ別基板の写真を受領。
CMのオスとT3PのPC専用メスの間へ挟める候補。端子間の結線・短絡・実通信は未確認。
以前のYC269基板とは別物として扱う。

写真の向きでは上列の中央付近が `B8 D− D+ B5`、下列は `A5 D+ D− A8`。
上下でD+/D−の位置が入れ替わるため、同じ列位置を同じ信号とみなさない。
GNDとSGND（シールド）も同一とは仮定しない。

まず新基板単体で、PC・CM・T3P・プローブをすべて外して抵抗測定する。
確認対象は上列D+対下列D+、上列D−対下列D−、VCC対GND、D+対D−。
最初の2つが開放でも直ちに不良ではなく、A/B側が独立した構成の可能性がある。
測定結果を受けるまでピン同士を追加接続しない。T3Pへのキー送信はまだ行わない。

ユーザー測定では上記4組すべてOL。③④は測った組合せに導通を検出しなかった結果。
①②はA/B側のデータ端子が独立している可能性と整合するが、配線構造の確定ではない。
まずプローブ同士を接触させて低抵抗を表示するか確認する。
正常なら、次は新基板のメス側をCMのオスへ接続し、新基板のオス側は空けたまま、
写真の下段D−をCH1、下段D+をCH2、両GNDをGND（SGNDでない方）へ移す。
CMのPC電源を外した状態で付け替える。再接続後もT3Pなしで信号の通る端子を確認する。
この段階で新基板の中継導通・波形を確認済みとは扱わない。A/B端子を追加短絡しない。

### 新基板の測定点を実測（第6回）

ユーザーが上記の新基板への交換を完了したと回答。T3Pなし、新基板のオス端は空けた状態で
一回だけ送信し、SINGLEのWAIT→STOPと全1M点を保存した。
実測ではCH2がCMのD−クロック、CH1がCMのD+データだった。
指定した下段表示との対応が予想と逆であり、表示の誤りやプローブの取り違え等の原因は未確定。
元データのチャネル名を変更せず、明示的にクロックCH2として解析した。

`scripts/analyze_cm_scope.py --frame 6 --clock-channel 2`:

- 16クロック、`0001011011101111` = `0x16EF`。
- High 9.666〜9.667µs、Low 9.625µs、データ先行124〜125ns。
- クロック平坦部約3.335V、データ平坦部約3.295V。ADCクリップなし。
- 物理チャネルCH1最大3.526V／最小−0.284V、CH2最大3.442V／最小−0.202V。
- PIO/CPU双方の出力許可0、欠乏・故障なし。今回もT3Pへは送信していない。

新基板の測定点までの信号を確認した結果であり、オス端を介したT3Pとの通信はまだ未確認。
CMを既検証のUSBホスト読取り用v2へ照合書込みで戻し、`host_requested=false`、D+/D−とも0を確認。
現時点のCMは波形用v3ではなく、ホスト開始前の読取り用v2。
次の物理操作はCMのPC電源を外してスコープ本体側CH1/CH2のBNC接続を交換し、
新基板のオスをT3PのPC専用メスへ挿す。T3Pの測定用電源端子は両方空ける。
通常USB通信の確認を先に行い、復旧キーは送信しない。

## 端子対応の修正と第7・8回（2026-11-01追記）

ユーザーが第6回のプローブD+/D−を逆に接続していたと確認し、CH1=D−、CH2=D+へ修正。
新基板の表示の誤りとは扱わない。その後、新基板越しに純正HID識別と設定読取りが成功した。

別件として、公式BR35 ROMの入力ビットとSDKの端子定義を照合した結果、
ROMは`PORTUSB.IN`のbit1、すなわちD−をデータとして読むことを確認。
従来の試験用v1〜v3は反対の候補（クロックD−／データD+）だった。
参照した外部説明はASCII図と説明文が食い違っており、過去の波形一致をROM適合とは扱わない。
過去6回はすべてT3Pを外した状態の測定。元データとv3ソースを保持している。

v4ではクロックD+=GPIO13、データD−=GPIO12へ修正し、周期・PIOでの出力解除は維持。
`analysis/rom-usb-evidence.json`は24命令、3相対呼出しとSDKのレジスター定義を照合する。
キー一致後の遅延呼出し先は、命令末尾から変位を足すと`0xFB7FC`と`0xFB8A2`。
後者は1000を前者へ渡すループで、引数1は公称約1msのLow保持と解釈される。
これは参照ROMの解析でありT3P上のACK実測ではない。

第7回は波形用v4、第8回は次の一回接続試験用プログラムのBENCHコマンド。
両回ともT3Pは外した状態。CH2の16立上りでCH1から`0x16EF`を読み取れた。
High 9.666〜9.667µs、Low 9.625〜9.626µs、データ先行124〜125ns、ADCクリップなし。
送信後はPIO自身の出力許可0、欠乏・故障なし。
第8回では波形用PIO/DMAを解放した後、識別専用USBホストの開始通知まで確認した。
この記録範囲は1msであり、ホスト開始の1.2ms待機そのものを波形で計時したわけではない。

再現: `scripts/analyze_cm_scope.py --frame 7 --clock-channel 2 --clock-line D+`（8も同様）。
図は`artifacts/cm-wave-scope/measured-frame7.png`と`measured-frame8.png`。
次の試験の詳細は[一回接続のROM識別試験](CM_ROM_PROBE.ja.md)。
